## Unreleased

- **New: `pkg/buildkit/ec2` on-demand builders (`Args.Mode: ec2.ModeOnDemand`) behind a wake proxy (`ec2.NewProxy`).** Updates `github.com/truvity/asg` from v0.4.2 to v0.6.0. A builder is one plain EC2 instance (`asg.Args.Single`; its run state is not Pulumi's) with a persistent encrypted 100 GiB gp3 cache volume (`asg.Args.Data`, in `OnDemand.Zone`, protected and retained on delete) mounted by asg's `datavolume` module at the daemon's state directory, so the cache survives stops, starts and image or user-data upgrades. The always-on proxy is asg's `cmd/wake-proxy` (v0.6.0, binary and sha256 pinned in `ec2.WakeProxyVersion` / `ec2.WakeProxySHA256`) on a `t4g.nano`-class appliance in the group mode (desired 1, one stopped warm-pool spare, launch hook, ELB health); it owns the shared NLB's listeners and target groups (TCP, idle timeout 3600 s, above the 180 s wake timeout; HTTP health check `/healthz`), starts the builder it finds by the `role` tag when a client connects, holds the connection until the daemon answers, pipes the TCP stream through (mutual TLS stays end to end) and stops the builder after 20 idle minutes. The builder's security group admits the proxy's group on 1234 only. The proxy's role is `wakeproxy.Statements` plus the volumes' KMS key when it is customer-managed.
  - What a single instance cannot have is replaced or dropped: the launch hook, in-service steps and ready check give way to systemd (`buildkitd.service` enabled, requiring the metadata guard, the certificate unit and the data volume); the certificate is fetched on **every boot** (`buildkit-cert.service`, asg ssmcert's own `load`) and rotated **in place when idle** (`buildkit-cert-check.timer`: on a new parameter version, once port 1234 has had no established connection for 5 minutes, load and restart the daemon) instead of through Standby; the group watchdog and the Standby rotation are dropped (`Restart=always` stays); the role loses every `autoscaling:` action.
  - New outputs: `Builder.InstanceID()`, `DataVolumeID()`, `SecurityGroupID()`, `RoleTagKey` / `RoleTagValue`; `Proxy.GroupName`, `SecurityGroupID()`, `HealthPort`, `MetricsAddress`, `Front`. `buildkit.Config` gains `OnDemand` and `BootUnits`.
  - **The default `Mode` is the group: existing consumers render byte-identically** (the three goldens are unchanged). Migration order: create the proxy and the on-demand builders, verify a build through the proxy (the data volume starts empty, so the first builds are cold), and only then delete the old group and its warm pool. docs/buildkit-on-ec2.md, "On demand".

## v0.1.4

- **Fixed: a BuildKit builder group no longer waits for capacity, so a long first boot cannot leave it without its warm pool.** Updates `github.com/truvity/asg` from v0.4.0 to v0.4.2. The builder groups have a launch hook, so a group is not InService until the first instance completes it, and that can take longer than the ten minutes the provider waits by default. The create then timed out after the group existed but before its warm pool was put, and the state recorded a pool that was never made: later updates did not create it either, so the group had no warm pool, silently. A group with a launch hook now has `WaitForCapacityTimeout` `"0"`; readiness is the hook's job. For an existing stack this is one in-place update of each group, no replacement. A stack that already lost its warm pool gets it back from a `pulumi refresh` followed by `pulumi up`.
- **Also from asg v0.4.1: a `front` target group has a name that fits AWS's 32-character limit.** The builder's listener now names its target group from the listener's name cut to 24 characters and a hash of what replaces it, where the autoname could pass 32 and be refused at preview. Nothing deployed from earlier releases created a target group, so there is nothing to replace. The `pkg/buildkit/ec2` resources golden gains `waitForCapacityTimeout` and the target group `name`.

## v0.1.3

- **Fixed: the BuildKit builders' cache volume is labelled `bkcache`.** `mkfs.xfs` refuses labels of more than 12 characters, so with `buildkit-cache` the first-boot script failed, the launch hook never completed, and no builder came into service. A test now holds the label to 12 characters.

## v0.1.2

- **New chart block `externalBuilders` (off by default): the TLS material of BuildKit builders outside the cluster.** Per architecture a cert-manager `Certificate` (`buildkitd-external-<arch>`) for the names clients dial, from the given issuer, and a `PushSecret` that writes its `tls.crt` and `tls.key` as `<arch>/cert` and `<arch>/key`; and one `PushSecret` that writes the client CA certificate as `client-ca`, read from `clientCA.key` (`ca.crt`) of a Secret in the release namespace (an external client's, whose `ca.crt` is the client CA). It is independent of `buildkitd.enabled`, so a release may render it alone. The refusals: no issuer, an architecture without names, no store, no client CA Secret, a remote name that is not a relative parameter path. docs/mtls.md, "Builders outside the cluster".
- **New `ec2.KeyPolicyStatement`:** the builder's part of the policy of the certificate parameters' key, `kms:Decrypt` by the builder's role (by `aws:PrincipalArn`, so the key may exist before the role) through SSM for the same three parameters as the role's own grant, one statement per builder.

## v0.1.1

- **`pkg/buildkit/ec2` registers no component of its own.** `ec2.New` returns a plain holder, and the box (`truvity:asg:Box`) and its listener (`truvity:asg:Front`) are registered with the caller's options. In v0.1.0 the wrapper passed itself as the parent to truvity/asg, whose own children then took the wrapper as their parent too (a caller's `Parent` overrides the library's), so the URNs would have moved the day that changes. Nothing was deployed with v0.1.0.

## v0.1.0

- **New Go packages `pkg/buildkit` and `pkg/buildkit/ec2` (module `github.com/truvity/ci-support`): the BuildKit builders on machines of their own.**
  - `pkg/buildkit` renders the daemon with no provider in it, as a github.com/truvity/asg module: `buildkitd.toml` (garbage collection, `max-parallelism`, the mutual-TLS listener, the debug address on loopback), the systemd unit (rootless through rootlesskit, `MemoryHigh` 85% and `MemoryMax` 92% of the machine, a lower CPU weight), the pinned BuildKit v0.33.0 and rootlesskit v3.0.1 releases (sha256 of the GitHub release assets), the cache volume (xfs, mounted from fstab) and an nftables table that drops traffic to the instance metadata service from every uid but root. The daemon starts only on a boot into service; the launch hook completes once `buildctl debug workers` answers.
  - `pkg/buildkit/ec2` runs it on an EC2 Auto Scaling group with asg v0.4.0: a listener of a shared NLB (`front.Attach`, TCP, idle timeout 3600 s), ELB health, a warm pool of one that takes a scaled-in instance back (`ReuseOnScaleIn`), a 100 GiB cache volume, launch-before-terminate refresh, the termination policy `NewestInstance`, asg's `ssmcert` module (the server certificate, its key and the client CA from SSM into `/run`; the nightly rotation through Standby) and asg's `watchdog` module. Its one grant of its own is `kms:Decrypt` of the certificate parameters' key, by alias, through SSM, for those parameters only.
- The CI Go job and `just test` cover the root module.

- Create the repository: the licence, the README, the contributing and security notes, the toolchain (`devbox.json`), the `Justfile` gate (`lint`, `leak-canary`), the leak canary and the CI workflow that holds the repository to the component contract. No chart, image or tool is published yet; the caches, the docker and nix builders and the `ci-builders` chart move here from truvity/ci-plane in a later migration, with their own entries.
- The leak canary's pattern for a private organisation's name is spelled so that the script itself does not contain the name.
- Move the `ci-builders` chart and cache-redirect here from truvity/ci-plane, with the chart's CI values, golden renders, refused fixtures and their checks (`golden`, `schema`), the digest stamper, the release-image and Renovate-coverage guards, the shared Go lint configuration and the chart's documents. The goldens are byte-identical to ci-plane's at the move.
- The chart's `cacheRedirectImage.repository` default is now `truvity/ci-support/cache-redirect`; the goldens change in exactly those image lines. cache-redirect's Go module path is `github.com/truvity/ci-support/image/cache-redirect`, its User-Agent names this repository, and its release image is labelled MIT (the repository's licence; the ci-plane label said Apache-2.0).
- The release workflow publishes the image to `ghcr.io/truvity/ci-support/cache-redirect` and the chart to `oci://ghcr.io/truvity/ci-support/charts/ci-builders` (not `ghcr.io/truvity/charts/ci-builders`, which keeps ci-plane's version line). It stamps `nixWorkerImage` and `runnerImage` with the digests of the ci-plane release `CI_PLANE_IMAGES` names (v8.0.0), so the chart stays digest-pinned to every image it can run.
- The gate gains `golden`, `schema`, `test` and `vuln` recipes; `lint` adds the chart lint and runs shellcheck at warning level. The leak canary gains ci-plane's per-pattern allowances for the documented placeholder account and registry and for templated or placeholder in-cluster Service names.
