# Changelog

Tags `vX.Y.Z` version the repository: charts, images and tools are released
together under one version.

## v1.1.3

- Fixed: the wake proxy no longer stops a builder seconds after it is created, which left the builder permanently unable to serve. The proxy is now truvity/asg v0.9.1 (`ec2.WakeProxyVersion` and `WakeProxySHA256` were v0.9.0; `github.com/truvity/asg` moves to v0.9.1). v0.9.0 counted an untagged builder's idle time from the proxy's own start, so a builder replaced by an apply (a new image, a new launch template version) was stopped at the first idle check, in the middle of its first boot; cloud-init's once-per-instance steps that were cut off (the package install) never re-ran, the IMDS guard unit then failed on every wake, and buildkitd never started. v0.9.1 counts idle time from the instance's launch as well. A builder replaced while an older proxy ran keeps the broken first boot: apply the new proxy first, then replace the builder. A new proxy release is a new launch template version, so the proxy instance is refreshed on the next apply.

## v1.1.2

- Fixed: the wake proxy the on-demand builders install is now truvity/asg v0.9.0 (`ec2.WakeProxyVersion` and `WakeProxySHA256` were v0.8.0). v0.9.0 exports `wake_proxy_connect_failures_total`, which the chart's `WakeProxyBuilderUnreachable` alert (v1.1.1) needs; with the v0.8.0 proxy the series was absent and the alert could never fire. A new proxy release is a new launch template version, so the proxy instance is refreshed on the next apply. Next release: v1.1.2.

## v1.1.1

- Fixed: `WakeProxyBuilderUnreachable` fired on every normal wake. It alerted on `wake_proxy_dial_failures_total`, which counts every dial attempt including the refused retries while a woken builder boots (about 4 per wake), and on `wake_proxy_resolve_failures_total`, which is per poll attempt too. It now alerts on `increase(wake_proxy_connect_failures_total[15m]) > 0`: a client's build got no builder connection after the wake and every retry. The description says so. This needs the wake proxy from truvity/asg >= v0.9.0; with an older proxy the series is absent and the alert stays silent (upgrade the proxy with this chart). Next release: v1.1.1 (a fix to a rule's expression, no API or value change).
- Fixed: the wake-proxy VMRule writes the CRD's `record: ""` default explicitly on every alerting rule, so Argo CD no longer reports it OutOfSync.

## v1.1.0

## v1.0.0

The next release is v1.0.0: this repository removes what no consumer uses.

### Breaking

- **Removed: the group mode of `pkg/buildkit/ec2` (an Auto Scaling group per builder).** On demand (one plain instance behind the wake proxy) is the only mode.
  - Go API removed: `ec2.ModeGroup`; the group-only `ec2.Args` fields `Min`, `Max`, `Desired`, `WarmPoolSize`, `SubnetIDs`, `NLB`, `Listener`, `Sources`, `CacheVolumeGiB` and `Watchdog`; `ec2.Builder.Front`; the constants `ec2.DefaultCacheVolumeGiB` and `ec2.DefaultHookHeartbeatSeconds`; `ec2.MinMaxSize`; `ec2.Fleet.LegacyGroup`, `ec2.Fleet.LegacyArchs` and `ec2.FleetBuilder.MaxSize`. Their goldens (`resources`, `userdata`, `policy`) and docs are gone.
  - Changed: `ec2.Mode` and `ec2.ModeOnDemand` stay, `ModeOnDemand` is also the empty `Mode`, and any other value is refused. `ec2.Args.OnDemand` is required. `ec2.Fleet.Validate` always requires a builder's `zone` and refuses `mode: group`; `proxy` is accepted without a mode condition. `ec2.New` no longer creates a listener, a target group or an Auto Scaling group; the wake proxy's own group (`ec2.NewProxy`, warm pool, launch hook and instance refresh included) is unchanged, and so are the on-demand builders' resources and goldens.
  - `pkg/buildkit`: the daemon is rendered for a single instance only. Removed `buildkit.Config.OnDemand` (now always the behaviour), `Config.CacheDevice`, `Config.ReadyTimeoutSeconds`, `buildkit.StartOrder` and `buildkit.WatchCheck`; the module no longer contributes an in-service step or a ready check, and does not prepare the cache volume (asg's `datavolume` module does). `buildkit.ReadyCheck` stays.
  - Migration: a consumer already on `ModeOnDemand` uses none of the removed fields (they were refused with it) and sees no resource diff. A consumer still on the group mode moves to on demand first (docs/buildkit-on-ec2.md, "Wiring") before it takes this release; a `mode: group` or `legacy_group` in a configuration file mapped to `ec2.Fleet` is refused by `Fleet.Validate`.
- **Removed: the in-cluster `buildkitd` of the `ci-builders` chart** (the StatefulSets and Services, their cache volumes, the `buildkitd-mtls-<arch>` set, the in-cluster server certificates, their NetworkPolicies and the `parallel` / `inPlace` modes). The BuildKit builders are `pkg/buildkit/ec2`'s, outside the cluster.
  - Values removed: `buildkitd.archs`, `image`, `initImage`, `cacheSize`, `maxParallelism`, `probes`, `resources`, `networkPolicy`, `size`, `podAnnotations`, `scheduling`; `buildkitd.mtls.mode`, `retirePlain`, `reloader`, `serverCertificate`, `networkPolicy`; and the top-level `sizes` (it sized only the builders and the Nix workers). A removed key now fails the render and names itself (`templates/removed-values.yaml`), so a stale values file cannot be silently ignored.
  - Kept: `buildkitd.enabled`, `buildkitd.mtls.enabled` and `buildkitd.mtls.clientCA` (the client CA, its policy and bundle, and `externalClients`, such as the serverless runners' client certificate and its PushSecret); `externalBuilders` (the builders' server certificates and PushSecrets); `cacheRedirect`, `bazelRemote`, `npmCache`; `nodeClasses`, `nodeClass`, `nodeSelector`, `tolerations` and `storageClassName`, which now place the caches only. The `ci-builders.additionalIngress` helper stays for cache-redirect.
  - The presets lose their builder parts: `presets/preview.yaml` and `presets/stable.yaml` no longer set `buildkitd.*` and refer to the class `cache-plane` only (`builders-arm64` and `builders-amd64` are no longer read); `presets/karpenter.yaml` keeps `storageClassName: gp3` only.
  - Migration: delete the removed keys from your values; do not list `presets/nix-workers.yaml` (below). Clients that dialled `buildkitd-<arch>.<namespace>.svc:1234` or `buildkitd-mtls-<arch>` must dial the EC2 builders instead. Delete the retired StatefulSets' PersistentVolumeClaims by hand; Helm and Argo CD do not delete claims.
- **Removed: the Nix workers (`nixWorkers`) and everything that served them.** The StatefulSets and Services, the `ssh-ng` login, the OpenBao host-certificate flow, the opkssh people pilot, the worker NetworkPolicy and ServiceAccount, `presets/nix-workers.yaml`, and the images' values `nixWorkerImage` and `runnerImage` (only the workers ran them).
  - Values removed: `nixWorkers` (all of it), `nixWorkerImage`, `runnerImage`. The release workflow no longer resolves or stamps the runner and nix-worker digests (`CI_PLANE_IMAGES` is gone); only `cacheRedirectImage` is stamped.
  - Migration: delete `nixWorkers`, `nixWorkerImage` and `runnerImage` from your values (each fails the render with its own message otherwise), drop `presets/nix-workers.yaml` from `valueFiles`, and delete the workers' `/nix` volume claims. Builds that need Nix fetch through the cache-redirect `/nix` front-end (`cacheRedirect.nix`).
- Chart tests: the cases, goldens and refusal fixtures of the removed components are gone; `just golden-update` regenerates the rest, and the cache-redirect, bazel-remote, npm cache, `externalBuilders` and `externalClients` renders are byte-identical to v0.4.1.

## v0.4.1

- **Changed: the target groups' deregistration delay for the on-demand builders and the wake proxy is 300 s (was 900 s).** `ec2.DefaultDeregistrationDelaySeconds` drops from 900 to 300. With 900 s, deleting or refreshing a builder or proxy Auto Scaling Group outlasted the AWS provider's ~10 minute drain wait ("waiting for Auto Scaling Group drain") and every instance refresh waited 15 minutes per instance. A BuildKit session still open 300 s after its target deregisters is now cut. Consumers will see an in-place update of each target group's `deregistrationDelay` on the next apply.

## v0.4.0

- **New: `ec2.ProxyArgs.MetricsListenPort`, `MetricsSources` and `MetricsListener` publish the wake proxy's Prometheus metrics on the shared NLB.** With `MetricsListenPort` set, the proxy gets a TCP listener and a target group on that port (HTTP health check `/healthz` on the health port, like the routes), the group is attached to it, the proxy's security group admits the NLB's group on that port, and the proxy binds `0.0.0.0:<port>` unless `MetricsAddress` names a non-loopback host with the same port. The metrics are then scrapable from inside the VPC at `http://<NLB DNS name>:<port>/metrics`, a name that survives instance refreshes. New output `Proxy.MetricsListenPort`. Unset keeps today's behaviour: the existing goldens are unchanged. docs/buildkit-on-ec2.md, "Scraping the proxy's metrics across the VPC".

## v0.3.2

- **Fixed: on-demand builders no longer show a perpetual `userData` update after a refresh.** Updates `github.com/truvity/asg` from v0.8.0 to v0.8.1, which makes a single instance (`asg.Args.Single`) ignore `userData` and `userDataBase64`. A refresh read the user-data back and reported a change on the builder instance every time, and applying it stopped and started the builder. The wake proxy is unchanged (`ec2.WakeProxyVersion` stays v0.8.0).

## v0.3.1

- **Updated: the on-demand BuildKit wake proxy is truvity/asg v0.8.0 (was v0.6.0): a TCP health probe no longer wakes the builder.** `ec2.WakeProxyVersion` and `ec2.WakeProxySHA256` follow the release, and `github.com/truvity/asg` moves to v0.8.0. The proxy now wakes a builder on the client's first byte instead of on connect (per-route `wakeOn`, default `data`; `firstByteTimeout`, default 30 s; the binary fills both itself). BuildKit clients speak first (TLS), so the routes keep the default and a build wakes the builder as before, while a bare connect, such as a load balancer's or a monitor's TCP probe, leaves it stopped. The `proxy.userdata.golden.yaml` golden gains the new pinned URL and digest.

## v0.3.0

- **New `ec2.Fleet` and `Fleet.Validate` (`pkg/buildkit/ec2`): the builders' shape rules, checkable before any resource exists.** A caller that keeps its builders in a configuration file maps it to `Fleet` / `FleetProxy` / `FleetBuilder` (plain values, no provider inputs) and calls `Validate`, which reports every problem at once: the mode (`group` or `on-demand`), a proxy and a legacy group only on demand, the proxy's and each builder's instance type, an architecture of amd64 or arm64, a listener and `max_parallelism` of at least 1, a zone and non-negative data volume for on-demand builders only, a group `max_size` of 0 or at least `ec2.MinMaxSize`, and no listener shared between a legacy group builder and an on-demand one. `Fleet.Archs` / `LegacyArchs` list the architectures sorted.

## v0.2.0

- **New: `pkg/buildkit/ec2` on-demand builders (`Args.Mode: ec2.ModeOnDemand`) behind a wake proxy (`ec2.NewProxy`).** Updates `github.com/truvity/asg` from v0.4.2 to v0.6.0. A builder is one plain EC2 instance (`asg.Args.Single`; its run state is not Pulumi's) with a persistent encrypted 100 GiB gp3 cache volume (`asg.Args.Data`, in `OnDemand.Zone`, protected and retained on delete) mounted by asg's `datavolume` module at the daemon's state directory, so the cache survives stops, starts and image or user-data upgrades. The always-on proxy is asg's `cmd/wake-proxy` (v0.6.0, binary and sha256 pinned in `ec2.WakeProxyVersion` / `ec2.WakeProxySHA256`) on a `t4g.nano`-class appliance in the group mode (desired 1, one stopped warm-pool spare, launch hook, ELB health); it owns the shared NLB's listeners and target groups (TCP, idle timeout 3600 s, above the 180 s wake timeout; HTTP health check `/healthz`), starts the builder it finds by the `role` tag when a client connects, holds the connection until the daemon answers, pipes the TCP stream through (mutual TLS stays end to end) and stops the builder after 20 idle minutes. The builder's security group admits the proxy's group on 1234 only. The proxy's role is `wakeproxy.Statements` plus the volumes' KMS key when it is customer-managed.
  - What a single instance cannot have is replaced or dropped: the launch hook, in-service steps and ready check give way to systemd (`buildkitd.service` enabled, requiring the metadata guard, the certificate unit and the data volume); the certificate is fetched on **every boot** (`buildkit-cert.service`, asg ssmcert's own `load`) and rotated **in place when idle** (`buildkit-cert-check.timer`: on a new parameter version, once port 1234 has had no established connection for 5 minutes, load and restart the daemon) instead of through Standby; the group watchdog and the Standby rotation are dropped (`Restart=always` stays); the role loses every `autoscaling:` action.
  - New outputs: `Builder.InstanceID()`, `DataVolumeID()`, `SecurityGroupID()`, `RoleTagKey` / `RoleTagValue`; `Proxy.GroupName`, `SecurityGroupID()`, `HealthPort`, `MetricsAddress`, `Front`. `buildkit.Config` gains `OnDemand` and `BootUnits`.
  - **The default `Mode` is the group: existing consumers render byte-identically** (the three goldens are unchanged). Migration order: create the proxy and the on-demand builders, verify a build through the proxy (the data volume starts empty, so the first builds are cold), and only then delete the old group and its warm pool. docs/buildkit-on-ec2.md, "On demand".

## v0.1.4

- **Fixed: a BuildKit builder group no longer waits for capacity, so a long first boot cannot leave it without its warm pool.** Updates `github.com/truvity/asg` from v0.4.0 to v0.4.2. The builder groups have a launch hook, so a group is not InService until the first instance completes it, and that can take longer than the ten minutes the provider waits by default. The create then timed out after the group existed but before its warm pool was put, and the state recorded a pool that was never made: later updates did not create it either, so the group had no warm pool, silently. A group with a launch hook now has `WaitForCapacityTimeout` `"0"`; readiness is the hook's job. For an existing stack this is one in-place update of each group, no replacement. A stack that already lost its warm pool gets it back from a `pulumi refresh` followed by `pulumi up`.
- **Also from asg v0.4.1: a `front` target group has a name that fits AWS's 32-character limit.** The builder's listener now names its target group from the listener's name cut to 24 characters and a hash of what replaces it, where the autoname could pass 32 and be refused at preview. Nothing deployed from earlier releases created a target group, so there is nothing to replace. The `pkg/buildkit/ec2` resources golden gains `waitForCapacityTimeout` and the target group `name`.

## v0.1.3

- **Fixed: the BuildKit builders' cache volume is labelled `bkcache`.** `mkfs.xfs` refuses labels of more than 12 characters, so with `buildkit-cache` the first-boot script failed, the launch hook never completed, and no builder came into service. A test now holds the label to 12 characters.

## v0.1.2

- **New chart block `externalBuilders` (off by default): the TLS material of BuildKit builders outside the cluster.** Per architecture a cert-manager `Certificate` (`buildkitd-external-<arch>`) for the names clients dial, from the given issuer, and a `PushSecret` that writes its `tls.crt` and `tls.key` as `<arch>/cert` and `<arch>/key`; and one `PushSecret` that writes the client CA certificate as `client-ca`, read from `clientCA.key` (`ca.crt`) of a Secret in the release namespace (an external client's, whose `ca.crt` is the client CA). It is independent of `buildkitd.enabled`, so a release may render it alone. The refusals: no issuer, an architecture without names, no store, no client CA Secret, a remote name that is not a relative parameter path. docs/mtls.md, "Builders outside the cluster".
- **New `ec2.KeyPolicyStatement`:** the builder's part of the policy of the certificate parameters' key, `kms:Decrypt` by the builder's role (by `aws:PrincipalArn`, so the key may exist before the role) through SSM for the same three parameters as the role's own grant, one statement per builder.

## v0.1.1

- **`pkg/buildkit/ec2` registers no component of its own.** `ec2.New` returns a plain holder, and the box (`truvity:asg:Box`) and its listener (`truvity:asg:Front`) are registered with the caller's options. In v0.1.0 the wrapper passed itself as the parent to truvity/asg, whose own children then took the wrapper as their parent too (a caller's `Parent` overrides the library's), so the URNs would have moved the day that changes. Nothing was deployed with v0.1.0.

## v0.1.0

- **New Go packages `pkg/buildkit` and `pkg/buildkit/ec2` (module `github.com/truvity/ci-support`): the BuildKit builders on machines of their own.**
  - `pkg/buildkit` renders the daemon with no provider in it, as a github.com/truvity/asg module: `buildkitd.toml` (garbage collection, `max-parallelism`, the mutual-TLS listener, the debug address on loopback), the systemd unit (rootless through rootlesskit, `MemoryHigh` 85% and `MemoryMax` 92% of the machine, a lower CPU weight), the pinned BuildKit v0.33.0 and rootlesskit v3.0.1 releases (sha256 of the GitHub release assets), the cache volume (xfs, mounted from fstab) and an nftables table that drops traffic to the instance metadata service from every uid but root. The daemon starts only on a boot into service; the launch hook completes once `buildctl debug workers` answers.
  - `pkg/buildkit/ec2` runs it on an EC2 Auto Scaling group with asg v0.4.0: a listener of a shared NLB (`front.Attach`, TCP, idle timeout 3600 s), ELB health, a warm pool of one that takes a scaled-in instance back (`ReuseOnScaleIn`), a 100 GiB cache volume, launch-before-terminate refresh, the termination policy `NewestInstance`, asg's `ssmcert` module (the server certificate, its key and the client CA from SSM into `/run`; the nightly rotation through Standby) and asg's `watchdog` module. Its one grant of its own is `kms:Decrypt` of the certificate parameters' key, by alias, through SSM, for those parameters only.
